# SOC Automation Validation

## Overview

This document records the validation of the automated SOC alerting workflow implemented in the Mini SOC Monitoring Lab.

The objective of the validation was to confirm that a security detection generated by Splunk could automatically trigger an n8n workflow and deliver a notification to the SOC analyst through Telegram.

The validated automation path is:

```text
Security Event
      |
      v
Splunk Detection
      |
      v
Scheduled Alert
      |
      v
Webhook Alert Action
      |
      v
n8n Webhook
      |
      v
Remove Duplicates
      |
      v
Telegram
      |
      v
SOC Analyst Notification
```

## Validated Use Case

The first detection integrated with the automation workflow was:

**SSH Brute-Force Detection**

This detection identifies repeated failed SSH authentication attempts inside the Mini SOC lab.

When the detection meets the configured alert conditions, Splunk triggers the alert and forwards the event to n8n.

## Validation Objectives

The validation was designed to confirm the following:

- Splunk detection logic remained operational.
- The scheduled alert triggered correctly.
- The Splunk Webhook alert action executed.
- Splunk successfully communicated with n8n.
- The n8n Webhook node received the request.
- The workflow started automatically.
- Duplicate filtering executed.
- The Telegram node executed.
- The final SOC notification was delivered.
- The automation did not replace the original Splunk investigation workflow.

## Failure Isolation

The automation layer is separate from the core Splunk monitoring environment.

If n8n or Telegram becomes unavailable:

- Splunk continues ingesting logs.
- SPL detections continue operating.
- Splunk alerts can still be reviewed manually.
- Historical events remain available for investigation.

This prevents the external notification workflow from becoming a dependency for the core SIEM detection capability.
